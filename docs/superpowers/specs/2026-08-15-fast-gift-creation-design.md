# Fast Gift Creation Design

## هدف

زمان انتظار کاربر برای دریافت لینک هدیه باید کوتاه بماند. ساخت هدیهٔ متنی نباید به آماده‌سازی یا بارگذاری تصویر وابسته باشد و رابط باید در تمام مدت وضعیت روشن و قابل‌فهمی نمایش دهد.

## تصمیم تأییدشده

لینک هدیه ابتدا با محتوای متنی و بدون تصویر ایجاد می‌شود. اگر کاربر تصویری انتخاب کرده باشد، رابط پس از نمایش لینک، فایل را در پس‌زمینه آپلود و به همان هدیه متصل می‌کند. شکست این مرحله، لینک و محتوای متنی را بی‌اعتبار نمی‌کند؛ فقط یک پیام قابل‌فهم برای تلاش دوباره نمایش می‌دهد.

## جریان داده

| گام | رفتار رابط | رفتار API |
|---|---|---|
| 1 | با فشردن دکمه، حالت «در حال آماده‌سازی لینک» نمایش داده می‌شود. | `create-gift` فقط داده‌های متنی را ذخیره می‌کند و لینک را بازمی‌گرداند. |
| 2 | کارت لینک بلافاصله ظاهر می‌شود و کاربر می‌تواند آن را کپی یا باز کند. | پاسخ شامل کلید یک‌بارمصرفِ سازنده برای اتصال بعدی تصویر است. |
| 3 | اگر تصویر انتخاب شده باشد، یک وضعیت غیرمسدودکنندهٔ «در حال افزودن تصویر» نمایش داده می‌شود. | تصویر آپلود می‌شود، سپس endpoint محدود `attach-image` فقط با کلید سازنده همان هدیه را به‌روزرسانی می‌کند. |
| 4 | با موفقیت، وضعیت تصویر به «افزوده شد» تغییر می‌کند؛ با خطا، خود لینک باقی می‌ماند و رابط گزینهٔ تلاش دوباره می‌دهد. | کلید سازنده فقط برای همین عملیات استفاده می‌شود و به بازدیدکنندگان لینک داده نمی‌شود. |

## کارایی

در اندازه‌گیری اولیه، درخواست‌های گرم API حدود ۰٫۲۴ ثانیه و نخستین درخواست حدود ۰٫۵۱ ثانیه طول کشیدند. رابط در اولین تعامل کاربر یک درخواست سبک برای گرم‌کردن اتصال ارسال می‌کند تا تأخیر شروع برای ایجاد هدیه کمتر شود. در عین حال، رابط هرگز لینک قطعی را پیش از دریافت پاسخ `create-gift` نمایش نمی‌دهد.

## خطا و آزمون

برای ساخت متنی، خطای API با پیام فارسی و امکان تلاش دوباره نمایش داده می‌شود. برای تصویر، خطا جدا از ایجاد هدیه مدیریت می‌شود و رکورد متنی حفظ می‌شود. آزمون‌ها باید مسیر hash لینک، قرارداد کلید سازنده، و مستقل‌بودن موفقیت ساخت متن از آپلود تصویر را پوشش دهند.
